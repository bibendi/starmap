# Design

## Context

Мотивация и границы изменения — в `proposal.md`, контракт — в `specs/assessment-periods/spec.md`.

`Quarter` уже хранит start_date/end_date и отдельные evaluation_start_date/evaluation_end_date, но требует year/quarter_number, сортирует и ищет предшественника по ним. Формы позволяют явно задать даты; календарные границы и отсутствие пересечений сейчас не гарантируются. По сообщению пользователя, в production пересечений нет; live-проверка базы в рамках планирования не выполнялась.

`QuarterStatusService` управляет активацией и переносом, `QuarterDataCopier` копирует оценки только сотрудникам, оставшимся в исходной команде. Закрытие модели утверждает draft/submitted оценки. Признак is_current независим от status: первый созданный период становится текущим даже в draft, закрытие не сбрасывает этот признак.

Проверка окна для edit/update/submit находится в `SkillRatingsController`; approve/reject/approve_all имеют собственные существующие ограничения. `evaluation_start_date == end_date` явно допускается модельным тестом. Не нужно менять это поведение под видом обобщения. В продуктовых документах встречается описание автоматического создания циклов, но в данном изменении сохраняется существующее ручное управление.

Все query objects привязывают снимок к quarter_id; Coverage/Maturity history берут последние десять не-draft кварталов. `TeamMetricsTool` распознаёт только YYYY QN. Таблица action_plans имеет quarter_id, но прикладные модель, контроллер и маршруты для неё отсутствуют.

## Goals / Non-Goals

**Goals:**
- Получить одну доменную модель с хронологией по датам и едиными правилами жизненного цикла.
- Полностью перевести внутренние и внешние интерфейсы на периоды без alias и адаптеров прежнего квартального контракта.
- Обеспечить целостность данных при миграции и конкурентном сохранении.

**Non-Goals:**
- Не вводить STI/подклассы для длительностей, команды с собственными календарями или повторяющиеся расписания.
- Не менять существующую семантику согласования, видимости, сравнения снимков или вводить дополнительные проверки статуса в rating actions.
- Не реализовывать отсутствующий UI/домен планов развития и не исправлять попутно несвязанные дефекты.

## Decisions

### 1. AssessmentPeriod как единственная сущность

Переименовать quarters в assessment_periods, Quarter в AssessmentPeriod, quarter_id в assessment_period_id у skill_ratings и action_plans. Переименовать связанные policy, status service и copier. Сохранить первичные ключи, значения, внешние связи и индексы уникальности оценок по пользователю, технологии и периоду.

Добавить строковый enum period_kind: monthly/quarterly/semiannual/annual/custom. Не использовать поле type: оно включает Rails STI. Удалить year/quarter_number после переноса и удалить ограничения name+year и year+quarter_number. Год и номер стандартного периода выводятся из дат; name остаётся сохранённой подписью, а идентификатором для интеграций служит id.

Использовать только AssessmentPeriod во всех слоях приложения. Quarter и прежние имена ассоциаций заменяются полностью; alias и адаптеры не создаются. Квартал остаётся значением quarterly в типе периода. Сохранность существующих данных обеспечивает миграция.

### 2. Календарный тип и явные даты

start_date/end_date — источник истины для интервала, сортировки и поиска. period_kind задаёт допустимые календарные границы для стандартных типов. Форма выбирает тип и год с номером месяца/квартала/полугодия; годовой тип требует только год, custom — две даты. Один доменный преобразователь/методы модели определяют границы, валидацию и стандартную подпись; не размножать вычисления по контроллеру и Stimulus.

Предлагаемые подписи: YYYY-MM, YYYY QN, YYYY HN, YYYY, а для custom — диапазон дат. Квартальные подписи остаются прежними; существующее name при миграции не переписывается. Пользовательский ввод произвольных названий не добавляется: его нет в текущих формах. Локализованное отображение дат выполняет представление.

Сохранить end_date > start_date, evaluation_end_date > evaluation_start_date и evaluation_start_date >= end_date, включительность окна. Не подключать сейчас неиспользуемую validate_evaluation_dates с лимитом 30 дней. Окно оценки не участвует в проверке пересечения оцениваемых интервалов. Стандартный новый период по умолчанию quarterly; форма предлагает последний завершившийся календарный интервал выбранного типа, без автоматического создания и смены частоты на основе истории.

Альтернатива — считать всё custom и иметь только диапазон. Она не даёт явной поддержки требуемых стандартных типов и согласованных подписей. Отдельные модели длительностей избыточны.

### 3. Пересечения и хронология

Пересечение: existing.start_date <= candidate.end_date AND existing.end_date >= candidate.start_date, исключая саму редактируемую запись. Проверка действует для всех статусов. Соседство разрешено со следующего дня, разрывы разрешены. previous_period выбирает запись с максимальным end_date < start_date; новых фильтров по status или типу не вводить.

Добавить модельную валидацию с en/ru ошибкой и PostgreSQL exclusion constraint по daterange(start_date, end_date, '[]') WITH &&. Range GiST не требует btree_gist, поскольку ограничение не содержит скалярного ключа. Ограничение защищает также от конкурентных запросов; контроллер переводит конфликт ограничения в ошибку формы вне откатившейся транзакции. Изменения индексов и constraint должны отражаться в db/schema.rb.

Сохранить независимый is_current. Для существующих инвариантов одного current и одного active использовать частичные уникальные индексы и транзакционную активацию с последовательным обновлением старого и нового current. Конкурентный конфликт активации возвращает штатную ошибку. Не добавлять запрет активации на основании текущей даты или новые фильтры предшественника.

Альтернатива — только model validation; она допускает гонку. Запрет пересечений лишь для active разрешил бы параллельные исторические снимки и неоднозначную динамику.

### 4. Перенос и аналитика остаются снимками

Activation, previous_period и все запросы используют одну и ту же хронологию. Существующие оценки переносятся как draft с прежним правилом команды; данные предыдущего периода не мутируются. Если копирование завершается ошибкой, активация и частичный перенос откатываются: copier не должен сообщать успешную активацию после подавленного исключения. Это ограниченная защита существующей операции, а не переработка сервиса.

Переименовать параметры и scopes quarter → assessment_period/period в приложении, не изменяя SQL-формулы и правила текущих/исторических статусов. Все сложные запросы остаются в существующих domain query objects; компоненты получают готовые данные. Каждый затронутый публичный метод query object должен сохранять или получить N+1 coverage согласно AGENTS.md.

History использует последние десять не-draft периодов, независимо от их длительности; frontend получает period_name вместо quarter_name и подпись оси «Период». Динамика — разность соседних снимков без агрегации, annualization или автоматического сравнения с таким же типом.

### 5. Единые внешние интерфейсы

Единственные административные маршруты периодов — /admin/assessment_periods, вложенный параметр форм — assessment_period. Удалить /admin/quarters, прежние route helpers и обработку вложенного quarter; redirect и преобразования старых параметров не добавлять. Все действия сохраняют существующие проверки авторизации и ограничения жизненного цикла. Обновить все ссылки и формы приложения на новые имена.

MCP `team_metrics` сохраняет team_name и использует единственный необязательный селектор period_id (integer) для любого типа. Удалить quarter из input schema и execute, удалить разбор YYYY QN. Без period_id используется AssessmentPeriod.current, включая существующую семантику is_current независимо от статуса. По подтверждению пользователя, MCP-вызовы в production ещё не используются, поэтому адаптер старого контракта не нужен.

Ответ для всех типов, включая quarterly, содержит team, period_id, period_name и прежние метрики; поле quarter удаляется. Авторизация команды выполняется до получения данных; неизвестные идентификаторы, отсутствие current и неправильные входы сохраняют MCP error responses. Старый quarter-параметр не обрабатывается и не преобразуется в period_id; отдельная логика совместимости или особый формат ответа для кварталов не создаётся. Не добавлять MCP-инструмент перечисления периодов в этой задаче.

Для админки и MCP выбран прямой переход на периодные контракты по согласованному решению. Существующий продуктовый процесс сохраняется через новые интерфейсы; прежние URL, параметры и классы не поддерживаются.

## Risks / Trade-offs

- Масштаб переименования затрагивает весь runtime → проверять все модели, controllers, queries, views, компоненты, графики, policies, MCP и test factories; остаточные quarter references допустимы для типа quarterly и его календарных вычислений, исторических миграций и проверок переноса данных/удаления старого контракта.
- Старые записи могут содержать нестандартные квартальные даты/дубликаты current/active, несмотря на отсутствие пересечений по сообщению пользователя → preflight проверяет все новые ограничения и останавливает миграцию с id конфликтов; не классифицировать молча как custom.
- Constraint блокирует также пересекающиеся черновики → это сознательное следствие единой последовательности, независимо от статуса.
- Переименование таблиц несовместимо со старым работающим кодом → применять миграцию в существующем автоматическом процессе деплоя; отдельный ручной порядок развёртывания не вводится.
- Разная длительность снижает сопоставимость темпа роста → сохранить текущие абсолютные показатели; не вводить новые показатели скорости развития.
- Возврат к квартальной схеме после появления неквартальных данных невозможен без потери информации → down должен отказать, если записи не представимы старой схемой.

## Migration Plan

1. Миграция запускается автоматически при деплое. В её начале AssessmentPeriodMigrationPreflight проверяет пересечения включительных интервалов, валидность дат/типизации кварталов, дубликаты current/active и целостность ссылок. Отдельная rake-задача или ручная проверка на production не требуется.
2. Если данные несовместимы, проверка выбрасывает исключение с диагностикой до изменения схемы. Миграция и деплой завершаются ошибкой; существующий процесс деплоя выполняет откат. Даты и историю автоматически не исправлять, отсутствующие evaluation dates не заполнять выдуманными значениями.
3. При успешной проверке транзакционная миграция переименовывает таблицу/ключи, заполняет quarterly, обновляет ограничения и индексы, убирает квартальные столбцы. Сохранить id и все payload-значения. Поведение проверяется миграционными тестами на изолированных схемах; отдельная эксплуатационная документация для этого изменения не создаётся.
4. Обратная миграция допустима только пока все интервалы представимы кварталами и сохранённые имена удовлетворяют старым ограничениям: восстановить year/quarter_number из start_date, старые индексы и имена таблиц/ключей. Иначе отказать до изменения данных; откат не удаляет и не округляет новые периоды.

## Validation

Проверить календарные границы, високосный февраль, переход через год, пересечения и смежность, редактирование черновика, ошибки конкурентного сохранения, независимость evaluation window, mixed-type previous_period, перенос и его откат, один active/current, состояния и прежние ограничения согласования. Прогнать request/policy/component/Stimulus/MCP регрессии и N+1 проверки затронутых queries.

Использовать let_it_be для общих записей только на верхнем уровне spec, build для неперсистентных проверок. Завершить полным RSpec, npm test, RuboCop через gemfiles/rubocop.gemfile, npm run check:js и Brakeman. Проверить en/ru, dark mode и отсутствие изменений формул на одинаковом наборе оценок.
